# Dirty Work Cleaner

> 面向审计基础执行工作的 AI 自动化工作流 —— 把实质性程序中最耗时的资料核查与整理环节，做成可复用的自动化流程。

审计实质性程序里，执行人员需要在合同、凭证、票据、函证之间反复核对金额、日期与摘要，逐项比对、逐条登记，再整理成底稿。这部分工作规则明确、重复度高，却占据了现场执行的大量时间。

Dirty Work Cleaner 把这部分「脏活」拆成可自动化的模块：**用规则引擎处理可判定的字段，用大模型只处理规则覆盖不到的语义判断**，输出结构化的异常清单供审计人员复核。

> **定位边界**：本系统是执行辅助工具，不是结论形成工具。
> 系统输出的摘要与建议不构成正式审计意见，关键判断由人工复核确认。

---

## 1. 问题：执行层的「脏活」

审计项目的核心价值体现在风险识别、判断与结论上。但在真实执行过程中，最先消耗项目组时间的往往不是这些高阶判断，而是大量基础性、机械性的底稿工作：

- **资料非结构化。** 凭证、发票、电子回单、扫描件、截图形态各异，信息无法直接用于自动分析。
- **核对高度重复。** 抽样清单、底稿记录与实际附件之间需要逐项勾稽，人工比对易遗漏、易返工。
- **判断口径不统一。** 证据是否完整、金额是否合理，主要依赖个人经验，缺少统一规则支撑。

这三件事共同构成了审计执行层的效率瓶颈：**数据无法直接利用 + 核查无法自动执行 + 判断无法标准化**。

## 2. 定位与边界

本项目不是「自动审计系统」，也不是泛化的问答机器人，而是一套面向审计证据审阅场景的智能审阅助手。

- **在流程上**嵌入审计执行环节；
- **在职责上**服务于人工复核；
- **在边界上**不替代注册会计师及项目经理的专业判断。

目标用户是直接接触大量原始资料的执行层：审计实习生、A1/A2 级初级审计员，以及承担底稿执行任务的项目成员。

## 3. 系统构成

### 3.1 一个工作台 + 三项核心能力 + 三项拓展能力

首页工作台承接任务状态、处理进度、结果卡片与审阅摘要。三个核心模块构成主链路，三个拓展模块覆盖实务中分散但耗时的辅助事项。

| 模块 | 类型 | 作用 |
|---|---|---|
| 首页工作台 | 工作台 | 统一呈现任务状态、处理轨迹、结果卡片与摘要 |
| OCR 处理 | 核心 | 凭证、票据、回单影像转文本，含清洗与字段提取 |
| 凭证核查 | 核心 | 附件需求、金额覆盖、异常状态的规则判断 |
| 一致性检查 | 核心 | 抽凭样本与实际凭证逐项勾稽 |
| 地址核查 | 拓展 | 函证地址与工商注册地址的坐标距离核实 |
| 企业信息填列 | 拓展 | 工商信息结构化，减少重复填表 |
| Supporting 整理 | 拓展 | 按科目归集 supporting 底稿并生成汇总 |
| 全局 AI 助手 | 辅助 | 基于前述运行结果的解释与建议 |

### 3.2 五层架构

```
输入层    接收图片、Excel、文本、抽样清单等资料
  ↓
处理层    OCR 识别 + 文本清洗 + 字段抽取
  ↓
判断层    规则引擎执行凭证核查与一致性检查
  ↓
辅助层    大模型负责异常归纳、结果解释与建议生成
  ↓
输出层    结果卡片、异常清单、风险等级、审阅摘要
```

### 3.3 主链路

```
资料上传 → OCR 识别 → 文本清洗与字段提取 → 凭证核查
        → 一致性检查 → AI 解释 → 人工复核
```

这条链路对应审计执行中的实际工作步骤。在规则冲突、字段缺失严重或金额差异过大的节点，系统停止自动推进并转入人工复核路径。

## 4. 关键设计取舍：规则优先，模型辅助

这是整个项目最重要的一个技术判断，也是审计场景的特殊约束带来的。

审计结论必须**可追溯到具体依据**——每一步判定都应该能回答「为什么这么判」，而不是「模型说是这样」。因此系统没有把关键判断交给模型，而是：

**规则引擎负责判定，大模型负责解释。**

具体到代码里：

- **附件需求判定**按费用类型走显式白名单。差旅费、销售费用、管理费用、研发费用、制造费用、运输费为「需要附件」；折旧、摊销、内部结转为「不需要」。规则未覆盖的类型默认需要附件并标注来源。
- **金额覆盖判定**带有明确的容差参数：附件金额 ≥ 凭证金额 × 95%，或绝对差 ≤ 50 元，即判定为覆盖。这个容差是显式配置，可按业务口径调整。
- **模型只在两个位置介入**：一是当附件需求遇到白名单覆盖不到的类型时做初判；二是生成异常归纳、风险解释和下一步建议。
- **模型置信度低于 0.75 时，判定结果回退到规则结论**，并在结果里标注 `（AI低置信回退）`，让复核者知道这个结论是怎么来的。

结果是每一行核查结果都带有 `判断方式`、`判断来源`、`AI 置信度` 三列，判定路径是可追溯的。

## 5. 运行效果

以下为本地实测结果（Python 3.13 / Windows，示例数据见仓库 `samples/`）。

### 5.1 凭证核查

输入一份标准化凭证文本（凭证金额 45,580.50，差旅费），附件 2 张发票、估计金额 45,580.50：

- **核查状态**：已到位
- **判断来源**：AI 初判，置信度 0.95
- **建议动作**：可进入 Docu 或后续程序

系统生成的 AI 复核意见：

> 【风险判断】该样本附件已到位且金额匹配，未发现异常，可进入 Docu 或后续程序。
> 【原因】1. 凭证金额 45580.5 与附件/估计金额 45580.5 一致，核查状态为已到位，人工确认覆盖为 yes，且未发现异常。2. 附件类型为发票、数量 2、是否同质为 True，代表性录入为 False，本次按纸质附件情况录入信息进行复核。
> 【建议】1. 按既定流程将该样本纳入 Docu 或后续程序，并保留人工确认覆盖记录。2. 后续如遇高重复/同质材料，可采用代表性录入方式简化处理，但应明确其非全量附件识别。

### 5.2 一致性检查

用 `samples/` 中的脱敏示例数据（7 条样本）实跑，五种状态全部命中：

| 一致性状态 | 数量 | 涉及凭证号 |
|---|---|---|
| 凭证缺失 | 1 | DEMO-2026-0004 |
| 金额不一致 | 1 | DEMO-2026-0002 |
| 日期不一致 | 1 | DEMO-2026-0007 |
| 多余凭证 | 1 | DEMO-2026-0006 |
| 一致 | 3 | DEMO-2026-0001，DEMO-2026-0003，DEMO-2026-0005 |

页面汇总：总样本 7、异常数 4、异常率 57%。

### 5.3 全局 AI 助手

关键点：助手读取的是**刚跑完那一步的真实结果**，不是历史文件，也不是凭空回答。

问「系统总结」，答：

> 【结论】本次会话已完成：一致性检查 7 条样本（异常 4 条）
> 【原因】上述统计只覆盖已执行过的模块，未执行的模块不计入。
> 【建议下一步】如需定位具体异常，可直接问「重点异常有哪些」。

问「当前重点异常有哪些」，答：

> 【结论】当前存在 4 项重点异常，其中"凭证缺失"和"金额不一致"风险最高，需优先核查。
> 【原因】
> - S-04（DEMO-2026-0004）：底稿有金额 150,000 元，但实际凭证未找到，属于凭证缺失，且该笔在抽凭清单内，说明应存在但未获取。
> - S-02（DEMO-2026-0002）：底稿金额 950,000 元与凭证金额 1,000,000 元不符，差额 50,000 元，金额不一致。
> - S-06（DEMO-2026-0007）：底稿日期 2026-01-18 与凭证日期 2026-01-19 不一致，存在跨日入账或记录偏差。
> - 样本序号为空、凭证号 DEMO-2026-0006：该笔不在抽凭清单中，却存在实际凭证，属于多余凭证，需确认是否误入或重复记录。
> 【建议下一步】
> 1. 立即向被审计单位索取 DEMO-2026-0004 的实际凭证，确认该笔支出是否真实发生。
> 2. 对 DEMO-2026-0002 的 50,000 元差额进行追查，核实是底稿漏记还是凭证多计。
> 3. 核对 DEMO-2026-0007 的日期差异，确认是否存在跨期入账。
> 4. 查明 DEMO-2026-0006 未在抽凭清单却出现凭证的原因，判断是否为抽样遗漏或账外凭证。

解释层的输出由大模型生成，措辞与归纳质量每次运行会有波动——实测中出现过样本序号对应错位的情况。这正是系统把**所有数值判定收敛到规则引擎**的原因：判定结果不依赖模型，模型只负责组织语言与归纳原因。异常清单与状态列才是可依赖的事实来源，模型输出仅作为复核线索。

## 6. 效率价值测算

以下测算基于原型验证场景下的合理假设，用于说明潜在节约空间，**不构成经营承诺，也不是实测数据**：

| 环节 | 假设值 |
|---|---|
| 人工逐笔处理 1 份凭证及附件 | 15 – 20 分钟 |
| 系统介入后单份处理（上传 + 结果核对 + 异常复核） | 6 – 8 分钟 |
| 单份节约 | 8 – 12 分钟 |
| 按 200 份样本的项目规模折算 | 1600 – 2400 分钟，约 **27 – 40 小时** |
| 按初级执行人员 80 – 120 元/小时折算 | 单项目节约约 **2160 – 4800 元** |

测算的落点不在「替代多少人」，而在于：只要系统能在凭证审阅、一致性检查这些高频环节稳定减少重复劳动、降低返工率，就具备明确的付费逻辑。

## 7. 可复现的演示路径

```bash
cd DirtyWorkCleanerWeb
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
copy .env.example .env      # 填入 DEEPSEEK_API_KEY / AMAP_API_KEY
run.bat                     # 或 python app.py
```

浏览器打开 `http://127.0.0.1:8080`，建议按以下顺序演示：

1. **首页工作台** —— 说明整体流程与模块划分。
2. **OCR 处理** —— 上传 `DirtyWorkCleaner/ocr_output.txt`，展示原始文本、字段提取与标准化凭证。注意：图片输入需要安装 PaddleOCR，文本输入不需要。
3. **凭证核查** —— 填写附件情况后运行，展示核查状态、AI 复核意见与可追溯的判定路径。
4. **一致性检查** —— 同时上传 `samples/sampling_list_demo.xlsx` 与 `samples/voucher_list_demo.xlsx`，展示五种异常状态与汇总指标。
5. **DWCAIcenter** —— 问「系统总结」，展示助手基于刚跑出的结果作答，再问「当前重点异常有哪些」。
6. **拓展模块** —— 地址核查、企业信息填列、Supporting 整理，说明覆盖面。

两个 API Key 都不是必需的：未配置 DeepSeek 时，需要 AI 的页面会给出提示，规则类功能不受影响；未配置高德 Key 时，地址核查降级为规则比对，不做坐标距离核实。

## 8. 当前边界

这些是当前版本的明确边界，也是下一步的改进方向：

- **跨模块状态。** 各功能页面目前独立运行，结果不跨页面持久化，不存在「上游结果自动带入下游」的会话状态。一致性检查需要自行上传两个文件，而不是自动承接凭证核查的输出。会话级的结果承接是下一步工作。
- **中文文件名。** 底层 Web 框架的 multipart 解析会丢弃文件名中的非 ASCII 字节。已加入按文件头的类型嗅探兜底，但**演示时建议统一使用英文文件名**。
- **输入格式。** 支持 `xlsx` / `xls` / `csv` 与图片格式，PDF 输入尚未支持。
- **OCR 依赖。** 图片识别依赖 PaddleOCR，首次调用会自动下载模型（数百 MB）。未安装时文本输入仍然可用。
- **并发。** 开发服务器为单进程同步模式，适合本地演示与小规模试用。生产部署建议前置 WSGI 容器，并补上大模型调用的请求超时。
- **模块副本。** `modules/` 与 `DirtyWorkCleaner/` 下各有一份相同的业务逻辑，前者是 Web 运行时依赖，后者保留命令行入口与测试样例。修改业务逻辑只改 `modules/`。

## 9. 技术栈与代码规模

| 层 | 选型 |
|---|---|
| 后端 | Python + Bottle（轻量 WSGI 框架） |
| 前端 | 服务端渲染 HTML + 内联 CSS/JS，无构建步骤 |

## 10. 行业背景参照

审计与会计工作的数字化、标准化方向已有较明确的政策与专业依据：

- 财政部《会计信息化发展规划（2021—2025 年）》，以及 2024 年《会计信息化工作规范》，强调会计数字化转型、数据安全与质量提升。
- 中注协 2024 年印发《注册会计师审计数据规范采购》等 4 项审计数据标准，推动行业数据标准体系建设。
- IAASB 于 2024 年发布 Technology Position，提出主动应对审计、鉴证与技术交叉带来的机会与挑战。
- AICPA 将 Audit Data Analytics 界定为通过分析、建模与可视化发现模式、识别异常、提取有用信息。
- IIA 2024 版《Global Internal Audit Standards》强调高质量执行、有效沟通与持续改进。

这些文件共同说明：围绕证据处理、异常识别和结果沟通的执行层数字化，已经具备现实基础。以上政策与标准的具体条款请以原文为准。

## 11. 项目来源

本项目源于 2026 年上半年毕马威（KPMG）AI 审计大赛参赛作品，由高校学生组成的跨校团队完成。原型阶段部署于云服务器用于比赛演示，当前仓库为代码归档与持续开发版本。

仓库中的示例数据均为虚构演示数据，凭证号以 `DEMO-` 为前缀，不对应任何真实业务。比赛相关的商业计划书、答辩材料与原始模拟凭证不在本仓库中。
